# Loading reliability and idempotency: local audit

This document is a design and evidence checklist, **not a migration or a release approval**. The current frontend mitigates pool failures but cannot repair PostgREST pool saturation or prove an ambiguous write has finished. No production SQL, settings, customer data, or deployment were changed in preparing it.

## Evidence and limits

The reported observations are HTTP 504 and `PGRST003` for `ff_bootstrap`, and six upstream attempts in some failed requests. `PGRST003` indicates a PostgREST pool acquisition timeout; it does not establish why connections were unavailable or establish that SQL in `ff_bootstrap` is slow. The origin of the six attempts has not been established. In the locked SDK's mocked transport tests, RPC POSTs are not replayed on 504; this does not rule out browser, proxy, gateway, or other upstream behavior in production.

The local session bootstrap coalesces a flight per identity and gates further attempts after pool/deadline failures until user retry. Reads have 15-second deadlines and retain prior confirmed slice data where possible. Guarded squad and league writes have bounded deadlines and report uncertain outcomes without automatic replay. This is risk reduction, not exactly-once processing. See `src/services/api.ts`, `src/hooks/useAuth.tsx`, and `src/hooks/useLive.tsx` for implementation and tests.

## Idempotency protocol to implement and review

The existing `ff_league_create(text,numeric)` and squad RPCs accept no client operation ID. The match lineup submission migration 20261116235900 provides a domain-specific example of idempotency, but does not cover these operations. A safe additive protocol must not change existing RPC signatures or remove old callers. Proposed requirements, **not yet implemented**:

1. A client creates a cryptographically random UUID per logical action before sending it, persists its identity and scope before transmission, and reuses it only for that action. A client-generated UUID cannot deduplicate two devices independently generating distinct UUIDs. A durable cross-device discovery mechanism or a separately reviewed business rule is needed to recognize the same human intent; league name is not a unique identity. Browser locks/BroadcastChannel are advisory only and cannot establish server correctness.
2. A versioned authenticated registration RPC inserts an operation row keyed by actor and UUID with an immutable kind, canonical typed arguments (or a collision-resistant digest), scope, and a `registered` state. Concurrent registration with identical parameters returns the original registration; mismatched kind, actor, scope or payload is rejected. Restrict direct table access and derive actor identity from the established `ff_private.current_actor_id()` mechanism. Retention, privacy, encryption of sensitive parameters, actor deletion and quotas must be decided explicitly. Never store access tokens or invite codes unnecessarily.
3. An execution RPC locks the operation row with a bounded lock wait, revalidates authorization at execution, and invokes the existing authorized domain function in the **same transaction** as recording its result. An already-completed operation returns its original result, not a new mutation. Concurrent submissions of the same operation serialize. The result, including relevant identifiers, is committed atomically with the mutation. Catching SQL errors in a PL/pgSQL subtransaction can record a sanitized definite failure only after the failed mutation subtransaction is rolled back; unexpected errors and transaction aborts must not be misreported as committed. Existing functions' nested definer ownership, grants, and hosted schema drift require explicit review.
4. A status RPC must distinguish registered, executing/locked, committed, definite failure and unknown. An absent receipt is **not** proof of non-execution: a registration or execution transaction can be in flight and invisible to a snapshot, or a network request can still arrive. A plain `SELECT` of a missing row cannot resolve that race. A robust cancellation/finalization protocol must synchronize with execution on the same durable operation row and prevent a later executor from committing after a terminal cancellation. Status results must not disclose another actor's operation or leak a league invite code after permissions change.
5. To prevent different operation IDs concurrently mutating a team, serialize on a server-side per-team key and apply existing team locks and revision/validation rules in an explicitly reviewed order. A scope lock on its own does not establish semantic deduplication of distinct intents. League creation similarly needs an agreed cross-device intent policy; inventing a uniqueness constraint on league names would break legitimate behavior.
6. Persist unresolved operation IDs across reloads and coordinate same-browser tabs with a bounded advisory mechanism plus durable state. On startup/account switch, discover and display this actor's unresolved operations without exposing previous account data; never blindly replay unknown squad writes. Recovery should query authoritative operation status and then read the squad or directory. An inaccessible status service must remain explicitly unresolved, not be treated as failure or success.
7. Add versioned local migrations through the repository's design/promote workflow, with narrow grants, `search_path`, ownership checks, compatibility tests for both repository migrations and the reviewed hosted 026 squad API, and rollback/retention review. Do not deploy frontend code that depends on new RPCs before their availability and compatibility have been verified. Legacy clients remain non-idempotent until migrated; an additive wrapper alone cannot protect them.

Required independent-connection PostgreSQL tests include same-ID and different-ID concurrency; lost responses after commit; rolled-back transactions; registration/execution/status race and delayed arrival; actor isolation and revoked access; repeated result retrieval; payload mismatch; locks/deadlock order; unchanged scoring, captaincy and gameweek behavior; existing data preservation; and migration/legacy-caller compatibility. Client tests need cross-tab coordination, account switch/sign-out, storage failure and unresolved states. None of these server guarantees should be asserted solely from a frontend mock.

## Loading-state audit and outstanding work

Initial auth/session, profile and directory recovery are bounded and have explicit retry handling in the existing local candidate; squad and match reads use bounded API read paths. League and squad ambiguous-write states deliberately show a warning and block repeat actions in the current provider. These guards are not durable cross-device operations. In particular, refreshing a squad while a timed-out server transaction could still commit does not prove finality. A fresh tab or storage failure can lose the pending create marker. More end-to-end tests against an isolated real backend are required before claiming all screens handle every failure safely.

## Evidence needed for production diagnosis

Collect time-correlated, access-controlled aggregate evidence with an operator's approval, avoiding tokens, SQL parameter values, customer records, and secrets:

- PostgREST pool configured size and acquisition timeout, in-use/idle/waiting connections, queue latency, request rate and errors broken down by endpoint and time.
- Database connection limit, connections by service and state, reserved slots, saturation over the incident window, and connection churn.
- CPU, memory, I/O, network and storage pressure at matching timestamps; baseline and peak workload.
- Transaction age, idle-in-transaction sessions and longest query durations using sanitized aggregates or approved observations; correlate to request IDs where available.
- Lock wait counts, duration, blocking relationships and lock types, distinguishing expected contention from deadlocks. Do not terminate sessions or change settings as part of diagnosis.
- Gateway/proxy timeout settings and sanitized request IDs, upstream attempt counts, retry policy and per-hop timings. Identify whether six attempts were separate browser calls, retries inside a proxy, or another source before attributing them.
- A controlled nonproduction reproduction of concurrency and pool limits, with database and PostgREST metrics, to separate query latency from queueing.

Do not increase compute, pool limits, or database connection caps based only on a frontend timeout; compare observed bottlenecks and operational limits first. Any production investigation or remediation requires separate authorization.

## Compatibility decision blocking universal duplicate protection

Local inspection on the current branch confirms that authenticated callers retain `EXECUTE` on `ff_league_create(text,numeric)` and the original squad RPCs (migration 20261115000011 and 017); the older create signature has no operation identifier. A separate receipt wrapper can safely deduplicate repeated calls carrying the same actor, operation UUID and immutable arguments. It cannot attach that UUID to a legacy call already in flight, nor can it tell a retry of `ff_league_create('Example',100000000)` from an intentional second create with identical arguments. A new client on device A and an older client on device B can therefore both create a league, or a delayed older squad request can commit after device A's receipt was checked. Existing per-team locks serialize some writes but do not make an unreceipted operation discoverable or prove no delayed request will arrive later. Two independently generated UUIDs have the same semantic-intent ambiguity, even if both clients use the new API.

This is a **scope/rollout decision**, not a claim that same-ID server idempotency is impossible. Choose and document one of these guarantees before claiming universal cross-device protection:

- Retain the legacy RPC behavior and explicitly limit idempotency to participating requests sharing an operation ID. Old clients and unrelated IDs remain outside that guarantee. During rollout, the UI must say that unresolved legacy requests cannot be ruled out.
- Require all mutation calls to carry a server-recognized operation identity and prevent unreceipted mutation entry points. This changes behavior for existing clients and needs an approved migration and compatibility/rollout plan, including old requests already in flight.
- Adopt an explicit business-level uniqueness/serialization policy that distinguishes duplicate intent from legitimate repeated actions. League names alone are not sufficient and a uniqueness rule would change existing product behavior.

No receipt migration or replacement client was added during this audit. The currently remembered tab-local create marker and in-memory squad lease do not close this boundary. Even after a protocol is designed, absent status must remain unknown until a synchronized tombstone/terminal state rules out a late request. The local executable migration chain does not contain design 026, whose squad RPC implementations differ from the executable chain; any future SQL must be tested against both the executable chain and the separately applied 026 fixture, without assuming either is the current production definition. No remote catalog was consulted in this turn.
