## Real-match architecture: implementation versus gaps

| Requirement | Actual tables, columns and constraints | Gaps / enforcement still required |
|---|---|---|
| Two actual teams in a match | `real_matches.team_a_id`, `team_b_id` have tenant-composite FKs to `real_football_teams(league_id,id)` and `check(team_a_id<>team_b_id)`; `gameweek_id` references `gameweeks` in the same league. | No client can create a match; future organizer RPC must authorize and validate metadata. |
| Registered players and temporary participants | `player_profiles` is the person, `real_team_players` maps same-league `(team_id,player_id)` with `valid_from`, optional `valid_until` and `valid_until>valid_from`; `temporary_participant_authorizations` maps same-league match/team/player and `authorized_by`, with a unique `(match_id,team_id,player_id)` and nonempty reason. | No FK or trigger connects a selected player to a valid roster at kickoff or to a temporary authorization. Neither roster overlap nor explicit revocation is modeled. The authorization's team is not constrained to either match side; its actor is a member, not necessarily a leader. `eligibility_evidence` is arbitrary JSON. Trusted, time-aware validation and authorized audit are mandatory. |
| Team selections | `real_match_lineups` connects `(league_id,match_id,revision_id)` to `match_revisions` and `team_id` to `real_football_teams`; `unique(revision_id,team_id)` permits at most one lineup for a given team in a revision. `real_match_lineup_players` connects to the lineup via `(league_id,revision_id,lineup_id)` and to `player_profiles` by same-league FK. | The lineup team is **not** constrained to Team A or Team B; exactly two sides and complete lineups are not enforced. |
| Starter/substitute and format | `real_matches.starters_per_side` is checked 1–11, `max_substitutes` 0–30. `real_match_lineup_players.selection` is checked `starter` or `substitute`. | Counts for each side, substitutions made, game format change handling and submitted format snapshot consistency are not enforced. |
| Position | `real_match_lineup_players.actual_position` is checked to GK/DEF/MID/FWD. | Per-format position allocation or player/team eligibility is not enforced. |
| No duplicate / both sides | `real_match_lineup_players.unique(revision_id,player_id)` prohibits the same real player twice anywhere in a **single revision**, including opposite sides. `(league_id,revision_id,player_id)` is also unique for event references. | Versions of the same match may legitimately repeat a player. Different revisions must not be merged as simultaneous live lineups; snapshot/approval logic is unimplemented. |
| Historical lineups | `match_revisions` has `unique(match_id,version)` and fields `state`, `match_snapshot`, scores; lineup and player rows refer to each version with `ON DELETE RESTRICT`. | Version rows and JSON snapshots are **not immutable** for privileged writers, and match metadata on `real_matches` is not frozen. `match_snapshot` defaults to empty JSON, not a validated historical record. No correction RPC, audit enforcement or reapproval exists. |
| Submit and review | `match_submissions` binds league/match/revision, `kind` is lineup/result, and `unique(revision_id,kind)`; `match_approvals` binds the exact submission/revision/kind and has one decision per submission. `result_requires_approved_lineup` requires the result submission to reference a lineup approval with `decision='approved'` and `kind='lineup'` for the same match. | `submitted_by`/`reviewed_by` reference league members, not necessarily an active organizer/leader; decision, state, reasons, eligibility and immutable content are not enforced by the schema. The result revision is not proven to match the earlier approved lineup. |
| Events | `match_events(league_id,revision_id,player_id)` references `real_match_lineup_players` and therefore the same revision/match; optional `related_player_id` has the same FK and must differ from the primary player. Nonempty `event_type`, nonnegative minute and positive quantity are checked; `details` supports extra data. | Event types are free text rather than an approved catalog. Rules for goals/assists/cards/substitutions, related player side/eligibility and score consistency are absent. Events for someone outside the lineup cannot be inserted even as an authorized correction; a controlled correction path and authorization model are still needed. |

## Security and scoring review

- `002_security.sql` enables RLS on every application table, revokes table privileges from `PUBLIC`, `anon`, and `authenticated`, then grants authenticated **SELECT only**. There are no client DML grants or mutation RPCs: ordinary managers, organizers and leaders are all unable to create or modify any match, approval, score or audit record. The local tests exercise examples, not every combination.
- In the original `002_security.sql` baseline, `is_organizer` is league-wide for match reads. Migration 004 deliberately replaces the match/revision read helpers with `is_match_organizer(league,match)`, requiring the exact match's organizer assignment plus active membership; temporary-authorization reads are narrowed the same way. That match-assigned rule is the Phase 2A.5 decision. Leader and organizer mutation/approval permissions are still not client grants: all authenticated table access remains SELECT-only, and future RPCs must separately enforce organizer submission versus leader approval.
- In the complete 001–006 sequence, ordinary members read approved match revisions; leaders can read league-wide match drafts; assigned organizers can read only their assigned matches. `official_match_results`, performances, scoring runs, fantasy-score summaries, fixtures and standings have broad active-league-member read policies. The policies assume future trusted writers only publish correct data; RLS does not validate approval or scoring lineage. Privileged roles/owners may bypass RLS and must be separately constrained. Check actual Supabase default grants, inherited roles and existing permissive Storage policies before deployment.
- `official_match_results` requires a composite FK to an **approved result** approval on the exact revision; `one_current_official_result` limits the current pointer per match. `match_player_performances` points to an official result and a lineup participant. However, `scoring_runs` has no input relation to official results, `fantasy_scores` has no FK to score items or approval, and `fantasy_score_items` does not prove its lineup belongs to the same gameweek/team or that the selected player is owned. Consequently, **no preapproval points are assured only for denied client DML, not for trusted owners/workers**. No worker exists. Complete run state and standings are not guaranteed approval-derived by DDL.
- `match_revisions.state` and approval decisions are not protected from privileged changes; `audit_logs` has member-linked actor and leader-only read, but nothing automatically inserts an audit or prevents its privileged modification. Correction authorization, append-only history, review and atomic recalculation are planned only.
- `fantasy_squad_players` primary key `(fantasy_team_id,league_player_id)` prevents a duplicate in one squad, while no league-wide ownership unique constraint exists. Tenant-composite FKs bind both team and player to the same league. The local test confirms two teams can own the same player and duplicate/cross-tenant inserts fail.
- Local PGlite read-policy tests simulate `auth.uid()` and check different leagues, draft visibility and write denial. Composite FKs reinforce tenant boundaries, but this is not a real Supabase JWT/PostgREST/Storage integration, role inheritance, concurrency or security audit.

### Deliberate owner-role gap witnesses

As a review experiment in a disposable in-memory PGlite database (not using authenticated client privileges), the migration owner successfully inserted a lineup for a third real team, selected a `registered` player with no roster row, recorded a manager as lineup reviewer, and inserted a positive completed fantasy score tied to a **draft** rule set while there were zero official results and zero audit rows. This confirms that relational shape and fail-closed client grants alone do not enforce these business invariants; do not enable workflow writes until reviewed transactions and tests close these gaps.

## Standings

Current frontend `src/data/competition.ts` sorts fantasy points descending and gives equal totals a shared rank. It is unchanged. Draft `head_to_head_fixtures` references fantasy teams and gameweeks, distinct from `real_matches`, and `league_standings.mode` distinguishes `fantasy_total` and `head_to_head`. The schema does **not** select a league default, compute H2H W/D/L or enforce 3/1/0, resolve ties or connect standing updates to an approved scoring run. Those remain proposed implementation and product decisions. Do not replace or silently change the current fantasy-total UI.

## Release blockers

Before any deployment or client writes: agree on rules and permissions; implement and independently review trusted actor checks, organizer assignment, roster/temporary eligibility, lineup/team/count constraints, immutable revision lifecycle, audited leader decisions and correction reapproval; create approved-result-to-run input linkage and transactional deterministic scoring/standings; validate Storage and role ownership on a local Supabase stack with concurrent adversarial tests. See [test plan and roadmap](test-plan.md).
