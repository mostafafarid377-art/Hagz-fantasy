# Real-match and fantasy-lineup workflow contracts

> **Phase 2A.1 supplement:** This document began as the 001–003 contract. Read with [offline hardening](phase-2a1-hardening.md), [Phase 2A.4 closure](phase-2a4-final-database-design-closure.md), and the superseding [Phase 2A.5 final decisions](phase-2a5-final-design-decisions.md). No live deployment is authorized.

These are **future transaction contracts**, not implemented RPCs. The SQL draft denies all client writes, including organizers and leaders. The 2A tests do not verify that an organizer can create a match or a leader can approve it. Names below are design labels, not callable APIs.

## Real-match lineage

Each `real_matches` identity belongs to one league and one gameweek, with distinct Team A/Team B and configurable `starters_per_side` and `max_substitutes`. Real matches are not fantasy fixtures. A `match_revisions` row is intended to become an immutable snapshot once submitted (not yet enforced); `match_snapshot` will contain the sides, date/time (UTC instant plus venue/time-zone context), gameweek, venue and format. The schema has not yet validated the snapshot payload or frozen root metadata: future RPCs **must** validate it and prevent editing the root after first submission. Correcting metadata is a new revision, not a silent rewrite. Revision states are `draft`, `submitted`, `approved`, `rejected`, and `corrected` (a correction draft requiring resubmission; it is not approval). Submissions have a separate kind, `lineup` or `result`.

### Create and submit lineup

1. Authenticated active **authorized organizer** calls the future `create_match` for their league. The server derives actor from `auth.uid()`, not any submitted actor/role. Team IDs, gameweek and organizer membership are rechecked in the same league; reject same team twice. Freeze valid format limits, date/time and venue into revision 1. Decide who may assign or revoke organizer status through a leader-only audited function; no self-granted organizer authority.
2. The organizer selects both real teams' registered players (or specifically **leader-authorized** temporary participants for that exact match and side), records `starter`/`substitute` and actual `GK/DEF/MID/FWD` position. Look up eligibility at match time using roster effective intervals (inclusive start, exclusive end) or a current signed-off temporary authorization; store an immutable eligibility snapshot. Reject cross-league, inactive/expired/revoked authority, duplicate participant on either side, or non-side team. The composite/unique SQL constraints backstop cross-league/duplicate cases; the eligibility checks are **not implemented**.
3. The future `submit_lineups` locks match and draft version; validates exactly the configured number of starters on **each** side, substitutions no greater than the configured maximum, unique player and team mapping, position and eligibility. Use format configuration rather than always 11; any incomplete lineup remains draft. Snapshot all data and an input hash; derive submitter from `auth.uid()`; set submitted and append audit in the same transaction. Repeated request with idempotency key must return the same submission, while concurrent edits or stale version fail cleanly. The schema currently lacks idempotency key and concurrency/version columns beyond revision version: add and test them before use.
4. A current active **league leader** locks and reviews the exact version and submits `approve_lineup` or `reject_lineup` with reason (reason required for rejection). Validate role and tenant inside the transaction, not a client flag. Only approval makes that snapshot eligible as a source. The one-decision unique constraint guards simultaneous decisions. Rejection is terminal for that immutable attempt; the assigned Organizer creates a new revision, submission and review rather than editing or resubmitting the rejected snapshot. For a correction, retain every attempt in the same open correction case and require that only the latest numbered attempt be approved/used. See the exact correction retry/approval invalidation contract in the Phase 2A.5 decision record.

### Events, results, and corrections

5. For match events and results, fork a **new draft result revision** from the approved lineup; keep the referenced approved lineup decision in the result submission. Validate the copied team membership/participant identities against that approved lineup; correction to the lineup requires a **new lineup approval** before result submission. Record goal, assist, own goal, yellow/red card, clean sheet, MVP, appearance, substitution or configured event kinds as separate idempotent events. `match_events` structurally references a selected participant in the exact revision, including any related substitution participant. Future RPCs must validate event semantics, same-side substitutions, legal transitions/timing, eligibility, goals vs score consistency, supported configurable event types and any correction authorization; they must not trust caller-provided minutes or identities without validation. A clean-sheet record is provisional until rules for minutes/conceded goals are confirmed.
6. `submit_result` locks the result revision, confirms the valid approved lineup of the same match and exact snapshot agreement, validates result and events, and submits. The leader approves or rejects the exact result revision, with rejection reason. Only an approved result decision for that exact revision can back an `official_match_results` row; SQL composite FKs bind match, revision, decision and kind. The future approval transaction must additionally check the leader role, state machine, immutable submission hash, score/event consistency and eligibility before inserting the official pointer. Clients cannot currently do any of these actions.
7. On a correction, never modify an approved submission, result, events or score in place. The Leader opens one immutable correction case with a reason. In one transaction mark the previously current official result non-current, supersede dependent scoring runs and mark standings stale; retain the prior result and approvals as historical facts. The UI must label that result superseded/under correction. Always require a newly approved lineup for the correction, then fork, submit and independently approve a result based on that exact approval before publishing a new official pointer. Each rejected correction-lineup attempt remains immutable and auditable; the Organizer starts a new numbered attempt copied from the rejected snapshot within the same open case. Only the latest attempt can be approved or source a result. A new case is not opened for a retry while the old case is unresolved. Preserve all old snapshots and approval records; superseded approvals become ineligible for new work, not deleted or rewritten.
8. Race safety: lock league/match/correction/attempt rows in a consistent order, use immutable versions and expected-version checks, unique keys for submissions/decisions and jobs, and deterministic retries. A result fork uses the stable business key `(league_id, match_id, correction_case_id, approved_lineup_approval_id, result_attempt_no)` (initial results use an initial-result case scope). Persist the mapping to one result revision in the same `READ COMMITTED` transaction as its copy and audit. Same-key replays return that revision; key/payload mismatch fails; deadlock retries replay the same key. A genuinely new result attempt is permitted only after a recorded result rejection and gets a new attempt number/request key. The correction-attempt and fork-idempotency records are design requirements for Phase 2B; migrations 004–006 do not implement them yet. An outbox written in the same commit as approval must protect scoring jobs from partial publication. If reviewer and organizer are the same person, self-approval remains forbidden.

## Fantasy roster and lineup contracts

A manager controls only their own `(league_id, manager_id)` fantasy team. A future transactional roster operation locks the team, reads current active league-player canonical state, verifies 15 maximum, unique player within that team, 2 GK/5 DEF/5 MID/3 FWD and budget (100,000,000 default, configurable), league market status, membership and snapshot price. Multiple managers can independently own the same real player. Existing inactive historical selections must remain available; reject new inactive selections. Transfers use a same-position outgoing/incoming player, budget and market checks and atomic price/history/audit; no fees or transfer limits are invented. Explicitly decide whether each transfer logs buys/sells as one transaction and how acquisition value affects budgets.

`confirm_fantasy_lineup` locks team/gameweek and snapshots exactly 15 selected players, 11 starters and 4 bench, allowed formation (`4-3-3` default, `4-4-2`, `3-5-2`, `3-4-3`, `4-5-1`, `5-3-2`, `5-4-1`), distinct C/VC, player position at lock, and prices (the nullable draft `price_snapshot` must be required by the trusted confirmation workflow). Slot order 1–11 is starters; 12–15 bench. Reject malformed squads, stale versions and edits after league deadline. Keep drafts separate, and supersede earlier confirmed versions atomically. Existing demo permits C/VC in the whole squad; whether a confirmed captain must start is unresolved. No automatic removal on a formation change; let the manager resolve a mismatch. Database DDL enforces uniqueness/slot range but **not** these aggregate/permission/deadline rules.
