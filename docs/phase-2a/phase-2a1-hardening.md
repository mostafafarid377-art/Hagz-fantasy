# Phase 2A.1 — offline integrity and security hardening

**Design prototype, not deployable; do not apply to a live project.** `supabase/design/migrations/004_integrity_workflows.sql` extends the Phase 2A drafts only in disposable, mocked PGlite tests. It adds triggers and prototype workflows but exposes **no authenticated or anonymous EXECUTE on mutation workflows**. It does not implement a scoring engine, publish fantasy points, connect the frontend, or run a Supabase stack. Existing Phase 2A documents describe the original 001–003 design and must be read with this supplement.

## Phase 2A review gaps and present controls

| Review gap | 004 prototype control | Remaining limitation |
|---|---|---|
| Lineup team not a match side; players need not belong to side | `guard_real_lineup` checks A/B; `guard_real_players` checks `real_team_players` at kickoff or `temporary_participant_authorizations` for exact match/team/player. Existing tenant FKs, selection/position checks and `unique(revision_id,player_id)` remain. | Team/roster activity is interpreted by `[valid_from,valid_until)` at kickoff; there is no overlap exclusion, temporary authorization revocation, or migration validation for pre-existing bad rows. |
| Counts and complete lineups not enforced | Player trigger locks the match and checks starter/substitute maxima; `validate_lineups` rechecks eligibility, exactly two sides, configured starter count and substitute limit on submission. | Concurrency/lock ordering has not been proven on actual PostgreSQL under parallel transactions. |
| Metadata/lineups could be rewritten | Match metadata is frozen after selection; lineup identity cannot be changed; revision content and lineup/event children freeze on submission; approval/submission records are append-only. Roster rows referenced by a selected lineup cannot be altered/deleted even in draft; existing restrictive FKs remain. | A privileged owner can disable triggers or change DDL; `match_snapshot` contents are still not validated against match metadata. Match-format/metadata correction and roster-retention policies require design; linked player/team display names remain mutable and need explicit historical-name snapshot semantics. |
| Members could be recorded as organizers/reviewers by a privileged writer | Submission/approval triggers and definer functions check `auth.uid()`, active membership, exact match's assigned organizer and leader, plus independent reviewer. Draft and temporary-authorization read policies also restrict organizers to their assigned match. Submitted/rejected/approved transitions and audit rows are trigger-driven. | No create-match or lineup-edit API is provided; there is no client workflow grant. Access depends on real verified JWT context and reviewed role ownership. |
| Approved result lineup might differ | `validate_submission` compares both complete player/side/selection/position/eligibility snapshots and match snapshot against the approved lineup, then requires a result approval. | Event catalog, event idempotency, substitution legality, goal/assist/card semantics and event-to-score reconciliation are not implemented. |
| Corrections lacked reapproval, invalidation and audit | `match_corrections` binds old official result, old and new revisions, actor, timestamp and reason. Leader-only `open_correction` forks a new draft; insert trigger marks old result non-current, supersedes dependent runs, marks standings stale and appends audit atomically. Later result forks/submissions must use the latest correction's newly approved lineup; leader review is then required for the new result. | The copied correction draft includes lineup only, not result events; a reviewed workflow for re-entering/diffing events is required. Prior current results are hidden as current immediately on opening correction; product must approve this behavior and handling of disputes. |
| Approved scores lacked source/rule lineage | `scoring_run_sources` references each exact official result/revision; source trigger checks current approved result, same league and gameweek; `scoring_runs` requires a pinned published rule version and a nonempty sealed source set at commit. Source rows and published rule values are immutable. `start_scoring` validates, sorts and de-duplicates source IDs and returns the same pending run on retry. | **No performance, score or standing calculation exists.** Triggers block their writes, including ordinary privileged owner DML; runs cannot become complete. This prevents publication rather than proving points are correctly calculated. Source completeness for a gameweek is unresolved. |
| Client could not be trusted with scores/audits | Original application-table DML revocation remains; new tables use RLS and no client DML; source rows and audit/approval/correction records are append-only. `fantasy_scores`, `fantasy_score_items`, `match_player_performances`, and `league_standings` inserts/updates/deletes are blocked, except leader-authorized stale marking of existing standings. | PostgreSQL owner/superuser can change or disable these protections. Storage policies, grants and real JWT handling have not been tested in Supabase. |
| Managers must not modify other fantasy teams | Existing `owns_team` and owner/leader read policies and same-league FKs remain; direct DML stays denied. | **No manager roster-management mutation function exists**; owner-only positive management functionality is not implemented. |

`real_match_lineup_players` uniqueness is per **revision**, allowing a player to be represented again in a subsequent historic version; the trigger prevents cross-side duplication in a single revision through the existing unique constraint. `guard_roster_history` conservatively prevents modifying/removing a referenced registration while any draft or submitted lineup uses it but does not solve backdated overlapping memberships or identity merging. `corrects_revision_id` is a same-league/same-match FK; `match_corrections` uses composite FKs to bind the official result and both revisions. `ON DELETE RESTRICT` keeps referenced history, but deactivation and legally compliant retention remain product decisions.

## Prototype function permission matrix

All functions listed below are `SECURITY DEFINER`, set fixed `search_path=pg_catalog,ff_private`, use schema-qualified resources, derive the actor from `auth.uid()`, and execute within the calling transaction. Their exact signatures are in 004. `PUBLIC`, `anon` and `authenticated` have **no EXECUTE grant** to these prototypes; a test-only `ff_test_gateway` is created inside `hardening.test.mjs` and is not a deployment role. This is an offline design, not a ready-to-expose RPC surface.

| Function | Intended actor (checked internally) | Effect |
|---|---|---|
| `authorize_temporary` | Active league leader | Record match/side/player authorization and audit. |
| `submit_lineup` | Active organizer assigned to that specific match | Validate both sides and lock a draft for review; audit submission. |
| `fork_result` | Assigned active organizer | Fork approved lineup into a new result draft; audit. |
| `set_result_score`, `record_event` | Assigned active organizer | Write a result draft / participant-linked event; audit. Submitted content cannot be changed. |
| `submit_result` | Assigned active organizer | Require scores and exact approved lineup snapshot; submit and audit. |
| `review_submission` | Active leader of that league, **not the submitter** | Approve or reject; rejection requires reason. Audit; result approval creates the current official pointer. |
| `open_correction` | Active league leader | Require reason, fork draft, preserve old rows, invalidate current result and dependent pending runs; audit affected IDs. |
| `start_scoring` | Active league leader through an explicitly authorized trusted server path | Create/retry a pending run with exact validated approved source set and pinned published rules; audit. Cannot calculate or publish points. |

Self-review is denied for both approval **and rejection** as a conservative prototype policy, not a final product decision. Since the schema permits only one active leader, an organizer who is also leader cannot review their own submission; they need a different assigned organizer under the current design. Whether multi-reviewer delegation or self-review can ever be allowed is unresolved.

Read helpers (including the new match-assignment check) are re-granted only as required for RLS; there are no client grants on new triggers or mutation prototypes. The mock test sets `request.jwt.claim.sub` directly, which is **not** evidence that an untrusted production user can safely set claims: actual Supabase auth/JWT verification, pool reset behavior, role inheritance, owner privileges, exposed schemas, default grants, extensions, and existing Storage policies require a real local stack and independent review. Do not expose a service-role key. A table owner or superuser can bypass RLS, disable triggers, modify functions or forge session context; use a dedicated least-privilege trusted owner and audited server gateway in a later approved phase.

## Scoring and idempotency details

`start_scoring` locks the gameweek and its matches, requires distinct current approved results in that gameweek, validates a published pinned rule set, and computes a deterministic key from sorted result IDs and the rule-set ID. The unique `(gameweek_id,input_hash)` constraint and source-set comparison make same-input retries return one pending run; the exact-set comparison also detects an MD5 key collision. The MD5 value is an idempotency key, **not** a cryptographic signature or evidence of input immutability. The run-source constraint trigger requires a sealed, nonempty set before commit, and additional sources are rejected once sealed. Correction supersedes runs referencing its old result and leaves their immutable source rows available for history.

There is intentionally **no function that accepts arbitrary scores**. Rule values remain empty by default; `match_player_performances`, `fantasy_score_items`, `fantasy_scores` and standing projections cannot be written. No final values, participation/bench/vice policy or H2H default is selected. A future approved scorer must derive event points from approved inputs, prove fantasy lineup/team/gameweek/ownership mapping, aggregate correctly, implement captain and vice rules, create standings from complete runs, validate all expected matches, atomically publish, and be tested for concurrent correction/retry/partial failure on actual Supabase. The 004 prototype does not meet those positive scoring requirements yet.

## Offline tests and remaining gates

`npm run test:db:design` runs two separate in-memory suites: the 10 original tests exercise **001–003 only** as a regression baseline, while `hardening.test.mjs` loads **001–004** and tests the new guards, gateways and role denials. It checks wrong side/roster, expired or unauthorized temporary participants, duplicate players, format limits, incomplete submissions, cross-league and self review, immutable revisions/rosters, mismatched result lineup, rejected result, unapproved/wrong-revision scoring sources, direct score/standing writes, idempotency, unauthorized corrections, audit tampering and correction reapproval. The test-only scoring values and identities never seed production.

No live migrations have been applied. The local PGlite mock does not verify Supabase Auth, PostgREST, Storage, inherited/default roles or transaction concurrency; a passing test is not a production security certification. Before deployment, review and test real role ownership, JWTs, RLS, lock ordering/deadlocks, race conditions, SQL privileges, multi-match source completeness, audit retention, correction policy, and performance on a disposable Supabase stack. `src/types/database.design.ts` and `types:db:design` still represent the original 001 design and intentionally have **not** been regenerated or connected to the frontend; the 004 shape needs separately reviewed generated types in a later approved phase.
