# Phase 2A.2 — PostgreSQL & Supabase compatibility audit

**Verdict: NOT DEPLOYABLE.** This is an offline design audit, not Phase 2B. PostgreSQL 15.18 executed the four SQL drafts together in a disposable local cluster using mock Auth, Storage and gateway roles. That demonstrates compatibility with the tested PostgreSQL environment and cases, **not** compatibility with an actual Supabase project, deployed JWT verification, PostgREST, Storage service, real grants or production concurrency. No live service was contacted. None of the SQL defects below was fixed in this audit; migration SQL remains the Phase 2A.1 prototype. A green vulnerability-witness test deliberately confirms a defect and is not a security pass.

## Confirmed blockers and required fixes

1. **Stale result approval after correction — confirmed, publication integrity (high).** A result can be submitted against an approved lineup, then `open_correction` supersedes the current official result and opens a new lineup draft, then the old pending submission can still be approved. `validate_submission` checks `require_latest_corrected_lineup` only at submission (`004:256–270`); `validate_approval` (`284–310`) does not recheck it. The approval trigger publishes a new current official result even though the correction lineup has not been approved. Reproduced using the mock privileged workflow on PostgreSQL. Fix by establishing a single locked match generation/current-correction invariant checked at approval/publication as well as submission; invalidate or reject stale pending submissions and drafts, ensure official insertion cannot bypass it, and test both transaction orderings and retries.
2. **Role revocation timing — confirmed, authorization (high if exposed).** `require_organizer`/`require_leader` read active membership without locking it (`004:67–83`); submission/approval check before waiting on the match lock (`245–253`, `284–293`). Two-connection PostgreSQL witnesses held a match lock, began a workflow, changed the organizer/leader to inactive and committed, then the waiting submission/approval committed. No authenticated client currently has workflow EXECUTE: the witness uses the explicit test gateway, so this is a blocker **before** exposing any privileged workflow, not a demonstrated current anonymous/client exploit. Define revocation semantics and serialize membership and organizer assignment changes with authorization and workflow changes using a consistent lock order, or an equivalently proven transaction protocol; recheck under lock and test revocation, reassignment, demotion and cross-tenant cases.
3. **Privileged direct writes are not a trusted publication boundary.** `001–003` deny client DML but a role with table writes can forge much of the workflow. In 004 the approval/official-result triggers improve checks, but trusted owners, roles with BYPASSRLS/table DML, TRUNCATE/trigger-management privilege, and claim-forging connections remain powerful. `guard_official_result` checks an already approved row, not the full correction invariant; `guard_run` allows leader-context supersession without requiring a correction; direct draft/rule/run writes are not necessarily audited or canonical. Do not expose service credentials or assume RLS confines a service role. Use a non-login owner, least-privilege gateway with only reviewed entry points, explicitly revoke table writes/TRUNCATE and default EXECUTE, control claim provenance and verify actual inheritance/effective grants; maintain atomic audit and defend every privileged entry path. Owner/superuser can still bypass guarantees and require operational controls.
4. **Roster eligibility race — code inspection, not reproduced here.** `guard_roster_history` (`004:169–184`) locks matches found through already-visible selected players. A concurrent registration update may see no uncommitted lineup selection while the selection checks an old registration version, leaving a selected player no longer eligible. The update has already locked the registration row before its trigger locks matches, while lineup writes lock match first; introducing registration locks naively can also produce a reverse-order deadlock. Design a consistent registration/match locking protocol or equivalent serializable retry discipline and test both insert/update/delete races; consider overlap/exclusion constraints for registrations.
5. **Source sealing against privileged concurrent writes — code inspection, not reproduced.** `guard_run_source` (`004:385–403`) locks the source match but reads `sources_sealed` without locking the run; `guard_run` can seal based on already visible source rows. Concurrent direct insertion into an unsealed run and sealing it may allow the insertion to commit after sealing. The tested `start_scoring` path is serialized for a gameweek, but that does not establish safety for roles allowed direct DML. Restrict DML and lock/recheck the run consistently during source insertion, sealing and correction; test with two connections and reversed ordering.
6. **Completeness, immutability and model gaps.** The scoring function accepts a caller-selected nonempty subset of current official results, not necessarily all relevant gameweek matches (`004:578–605`). It does not snapshot fantasy lineups, complete scoring, calculate points or publish standings. A hash only over rule and requested source IDs is insufficient for future complete scoring inputs and cryptographic collision resistance; retries return an existing pending run only after comparing sources. `match_snapshot` may default to `{}` and is not validated against actual match metadata, even though equality with the approved lineup is checked. Add an explicitly approved snapshot/completeness specification and immutable deterministic inputs. Fantasy squad size/positions/budget, exact starter/bench composition, captain/vice placement, same-position transfer, deadlines, fantasy lineup creation/versioning and event semantics remain future validation work; retain historical inactive selections and multiple ownership. Do not invent scoring values or switch ranking modes.

## Security and SQL review

- `001` uses UUID primary keys, league-scoped composite FKs, nonnegative scores, constrained enums/checks, `UNIQUE` and partial unique indexes: one active leader, one confirmed fantasy lineup per team/week, one captain and vice, one current official result per match and one complete run per gameweek. `unique(revision_id,player_id)` prevents selecting a real player for both sides of one revision; fantasy squad PK permits the same player across different fantasy teams. Most FKs restrict deletion. Indexes support membership, player lookup, market, transfers, matches, lineups/events, fixtures, notification and audit lookups; FK referencing columns are not universally indexed, so workload/EXPLAIN and lock-duration review is required, not a blanket index-pass claim. Some checks are at-most-one rather than exactly-one and cannot enforce multirow completeness.
- `002` enables RLS on its enumerated public tables and explicitly revokes client DML then grants SELECT; 004 does the same for its two tables. Most tenant data uses `is_member`; private squads/lineups/transfers use owner or leader; draft match content uses match/revision helpers; suggestions, notifications and audits have narrower predicates. `004` narrows organizer reads to assigned match. These are policy definitions, not proof against existing real-project permissive policies, inherited grants, column grants, views, exposed schemas or BYPASSRLS. `003` adds only a bucket-scoped SELECT policy; PostgreSQL test confirms an active member can read a valid referenced path and rejects a traversal-shaped path. The UUID filename character class accepts 36 hexadecimal/hyphen characters rather than enforcing canonical UUID positions; actual access still requires a matching stored reference. Upload byte validation, object lifecycle/reference safety, URL handling and actual Storage authorization remain open.
- `SECURITY DEFINER` helpers use `search_path=pg_catalog,ff_private` and qualified `public`/`auth` objects. `002` revokes CREATE on public for listed roles, restricts private schema access and restores selected read-helper EXECUTE; `004` revokes function EXECUTE then restores only read helpers. Test catalog and denied-client checks passed in the mocked setup. This assumes `ff_private` is trusted, owner legitimately bypasses RLS and cannot be impersonated, and no other inherited grants exist. Creating new functions normally grants EXECUTE to PUBLIC until revoked: execute each complete reviewed migration atomically, set safe default privileges for the *actual creating role*, audit intermediate access and validate actual owners, search paths, role memberships, PUBLIC and service-role grants. Migration environment/default privileges and Storage ownership are not known here.
- The mock `auth.uid()` reads `request.jwt.claim.sub` directly. A DB session allowed to set claims can impersonate users. Actual verified JWT `sub`, claim naming, `auth.uid()`, connection pool reset, gateway routing, RLS evaluation, expired/revoked tokens and error behavior must be tested through actual Supabase Auth/PostgREST with representative roles; no mocked claim is evidence of JWT authenticity.
- PostgreSQL treats each invoked function and its triggers as part of the calling transaction; failed constraints/trigger exceptions roll back their enclosing statement/transaction. `require_run_source` is `DEFERRABLE INITIALLY DEFERRED`, so an unsealed/empty run is rejected at transaction commit; 004's normal function creates sources and seals in one transaction. The adapter sent each full SQL file as a separate multi-statement simple query, not one transaction across all four files. No real migration runner rollback, upgrade from populated data, partial rerun, rollback migration or DDL ownership was tested. Draft files contain non-idempotent CREATE/ALTER statements and assume ordered pristine setup.

## Concurrency assessment

- **Submission versus revision child edits:** both normally lock match then revision in 004 (`guard_revision_child`, `validate_submission`), so they serialize under the intended workflow; a unique constraint and state checks help reject duplicate submissions. Authorization and roster caveats above still apply. Parent metadata and selected-registration guards are not a general proof across all writers.
- **Review versus review:** match row lock and unique `match_approvals(submission_id)` protect the tested design against two successful reviews of the same submission; duplicate requests are errors, not idempotent responses. The stale-result witness is a sequential ordering bug, not dependent on a race. Correction/review must be revalidated after locks.
- **Revision creation:** `fork_result` and `open_correction` lock the match before `max(version)+1`, and unique `(match_id,version)` protects against duplicate versions. Two simultaneous forks produced distinct versions, but created two drafts: no retry/idempotency key. Direct revision insertion does not use that protocol; concurrent arbitrary writers can conflict and callers need retries or restricted DML. Future fantasy lineup version creation is not implemented; its unique index alone does not provide an allocation workflow.
- **Scoring retries/corrections:** `start_scoring` locks gameweek then all its matches in UUID order, validates sources, and the two simultaneous identical calls returned the same pending run. `open_correction` locks match then current result and supersedes affected runs atomically with its correction insert, in the tested sequential cases. Cross-operation direct DML, reverse lock paths, gameweek changes, source sealing, two corrections, deadlock/serialization retries, multi-match coverage and production isolation levels remain unproven. Document a global lock graph (membership, gameweek, matches ordered, revision, registrations, result, run and sources), reconcile differing existing orders, and exercise controlled parallel transactions including failures, timeouts and rollback. Do not assume tests prove deadlock freedom.

## Reproduce disposable native tests

Requires Linux x64 and Node/npm. Use a **fresh** `/tmp/ff-pg-audit` cluster each run; the tests create global mock roles and data and do not clean them. The test refuses a TCP socket or a server data directory outside `/tmp/ff-pg-audit/`. Never point it at a Supabase or any non-disposable cluster. The following commands illustrate the setup used (choose a new data directory for each run):

```sh
mkdir -p /tmp/ff-pg-audit/socket
npm install --prefix /tmp/ff-pg-audit --no-save --no-package-lock \
  @embedded-postgres/linux-x64@15.18.0-beta.17 pg@8.16.3 --no-audit --no-fund
PG=/tmp/ff-pg-audit/node_modules/@embedded-postgres/linux-x64/native/bin
"$PG/initdb" -D /tmp/ff-pg-audit/fresh-data --no-locale -E UTF8 -A trust -U audit
"$PG/pg_ctl" -D /tmp/ff-pg-audit/fresh-data -l /tmp/ff-pg-audit/postgres.log \
  -o "-c listen_addresses='' -c unix_socket_directories=/tmp/ff-pg-audit/socket -c port=55432 -c unix_socket_permissions=0700" start
FF_PG_AUDIT_SOCKET=/tmp/ff-pg-audit/socket \
FF_PG_AUDIT_DRIVER=/tmp/ff-pg-audit/node_modules/pg \
  node --test supabase/design/tests/postgres-compat.mjs
"$PG/pg_ctl" -D /tmp/ff-pg-audit/fresh-data stop
```

`postgres-compat.mjs` adapts the existing seven hardening tests to node-postgres, then adds two parallel positive observations, three defect witnesses and a Storage policy case. The mock gateway has EXECUTE only on selected workflow signatures and sets mock actor claims. The initial test harness had a parameter binding error, fixed before the clean final run; an initial image-regex hypothesis was disproven and corrected to test the actual expected behavior. No existing test was weakened or removed.

## Tests and remaining validation

- Native PostgreSQL 15.18, fresh disposable Unix-socket-only cluster: **13/13 test cases executed successfully**, including three passing *defect witnesses* confirming unsafe behavior and therefore deployment blockers. 001–004 executed with mock setup; tested in PostgreSQL, not actual Supabase.
- `npm test`: 36/36; `npm run test:db:design`: 17/17 PGlite mock cases; `npm run typecheck` and `npm run build`: passed. PGlite is not evidence of Supabase compatibility.
- `npm run test:pages:assets`: passed; full Playwright suite: 42/42; Pages Playwright: 2/2. Both browser suites used the temporary Chromium 153.0.8010.0 and NSS libraries rather than Playwright's pinned Chromium 159.0.8154.6. The previously unreproduced responsive failure did not recur; its original cause remains unknown.
- `git diff --check`: passed. One verification command initially used the nonexistent script name `test:pages-assets`; the correctly named `test:pages:assets` and the browser suites were then run successfully.
- Actual target PostgreSQL version/extensions, migration role/permissions, RLS and inherited grants, Auth/JWT provenance, PostgREST RPC exposure, Storage and signed URLs, triggers under real ownership, multiple sessions/isolation levels and production-sized performance remain unverified. A future authorized disposable local Supabase stack and dedicated staging review are required; never apply this draft to a live project.
