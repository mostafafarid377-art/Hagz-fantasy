# Phase 2A.3 — offline PostgreSQL security hardening

**Status: ready for human security/design review only; NOT deployable or fully Supabase-compatible.** The confirmed Phase 2A.2 exploit scenarios were reproduced against 001–004 first, then rejected in native PostgreSQL tests using the additional offline draft `005_concurrency_hardening.sql`. Actual Supabase, production role grants, JWT verification, Storage and concurrency under a live deployment were not tested. No frontend integration, approved scoring algorithm, final scoring values or publication was added. Several unresolved issues and a failing native legacy test remain below.

## Revision and approval model — important unresolved requirement

Every submission already has an exact `(league_id, match_id, revision_id)` foreign key; its revision content becomes immutable after submission and its approval FK includes that same revision and kind. The existing design deliberately forks a **separate result revision** from the approved lineup revision. The result submission references the exact approved lineup approval in the same match; 004 validates that the copied lineup and match snapshot are identical, and 005 checks that this exact approved lineup remains eligible at result approval and official-pointer creation. Therefore **lineup approval and result approval do not literally refer to the same revision ID**. This is not a claim that the user's literal same-revision requirement has been met. A reviewer/product decision is required: approve this explicit two-revision lineage, or redesign the data model and workflows so both approvals target a single immutable revision. No incompatible schema redesign was silently invented here.

The prototype treats a newer submitted revision of the same kind as superseding an older one and the latest approved lineup as the current source; product review is needed for rejection/retry semantics. In particular, once a correction lineup is rejected there is no implemented safe workflow to fork/retry that correction: the latest correction requires its exact draft. Direct privileged writes, arbitrary revision creation and operator recovery require further design.

## New and replaced database objects

`005` adds functions `require_read_committed`, `require_current_lineup`, `guard_submission_generation`, `lock_roster_player`, `guard_roster_overlap`, and `guard_lineup_roster_lock`, and triggers `zz_guard_submission_generation`, `zz_guard_roster_overlap`, `zz_guard_lineup_roster_lock`. It replaces `require_organizer`, `require_leader`, `validate_approval`, `review_submission`, `guard_official_result`, `open_correction`, `guard_roster_history` and `guard_run_source`. It runs an overlap preflight check; it adds **no new declarative constraint or index**. The original tenant FKs, unique submission/approval, revision/version, lineup and scoring-run constraints and RLS remain. The no-cross-team-overlap invariant is trigger/advisory-lock based, not a PostgreSQL exclusion constraint; future deployment should consider a reviewed `btree_gist` exclusion constraint and migration of existing conflicts.

Client permissions remain fail-closed: the 005 final revoke restores only the read-policy helpers granted by 004. Workflow EXECUTE grants exist solely in the test gateway. RLS, tenant FKs, score/performance/standings write blocks, and absence of client DML are unchanged. A superuser, owner, trigger-disabling role, BYPASSRLS role or role with direct privileged writes/claim forging remains outside these guarantees. Revoke default PUBLIC execution atomically as part of a reviewed real migration and verify effective role memberships.

## Transactions and concurrency

- Match workflows use PostgreSQL `READ COMMITTED`. The new critical helpers reject other isolation levels with `25001`; this prevents relying on an old repeatable-read snapshot after an advisory-lock wait. The selected paths were exercised under READ COMMITTED and a repeatable-read fail-closed case was tested. This does **not** imply all existing privileged database paths are safe at all isolation levels.
- Organizer: match `FOR UPDATE` → active member `FOR SHARE` → organizer assignment `FOR SHARE`; review and correction: match `FOR UPDATE` → leader membership `FOR SHARE`. The locks persist until transaction end. A revocation committed first is observed by the workflow; one that starts after the share lock must wait until the operation commits/rolls back. Match lock serializes review with correction and other match writers. SQL function, triggered validation, state change, official pointer and audit execute within the caller's transaction; any exception aborts the statement/transaction.
- Roster: match/lineup writes use match then revision then per-player `pg_advisory_xact_lock(hashtextextended(...))`, followed by an eligibility recheck; registration updates already hold the updated row before their BEFORE trigger acquires per-player advisory locks and then relevant match rows. Different player keys for updates are sorted; hash collisions only cause extra serialization. Concurrent cross-path lock inversion can deadlock: PostgreSQL must abort one transaction (`40P01`) and the caller must retry the **whole** transaction. These tests do not prove a global deadlock-free lock order. Roster `TRUNCATE`, disabled triggers, ownership or unreviewed privileged bypasses are not protected.
- Scoring retains gameweek lock → ordered match locks in `start_scoring`; source insert locks match → run; correction locks match → result → affected runs. Concurrent run sealing and direct source insertion have reverse acquisition potential because UPDATE locks the run before its trigger. PostgreSQL may abort on deadlock; future gateways must handle whole-transaction retries. A committed unsealed run is normally prevented by the deferred source/seal constraint; the concurrent source test used a sealed run held by another transaction, **not** a constructed unsealed seal race. Multi-match lock cycles, every direct-DML ordering, lock timeouts and load/stress behavior are not exhaustively tested.
- Existing source rows pin both official result and revision by composite FK; correction marks affected pending runs superseded and stale sources cannot be used through tested APIs. The prototype allows caller-selected subsets of current gameweek sources and does not snapshot all eventual scoring inputs. No completeness policy or scoring publication is implemented. Retries produce a single identical pending run; result forks still produce multiple drafts on retry.

## Testing evidence

- Pre-fix fresh PostgreSQL cluster: 2A.2 witness suite 13/13 cases ran; the three named exploit witnesses **confirmed vulnerabilities**, not security success.
- Post-fix fresh PostgreSQL 15.18 cluster, mock setup: `postgres-security-2a3.mjs` **25/25 pass**, including actual rejection of all three original exploits, conflicting reviews, both correction/approval orderings, roster change versus selection both ways, conflicting registration, duplicate lineup selection, concurrent scoring retries, correction versus retry, sealed source lock and repeatable-read fail-closed check. Uses independently connected transactions and observes blocked backends via `pg_blocking_pids` where applicable. PostgreSQL was Unix-socket-only and stopped afterward.
- Separate PostgreSQL native legacy `postgres-design-2a3.mjs` against 001–003: **9/10 pass, 1 fail**. The delete of a referenced real match was correctly blocked, but PostgreSQL reported FK violation `23503` (`match_revisions_league_id_match_id_fkey`) while the existing `design.test.mjs` explicitly expects restrict violation `23001`. This can depend on which of several referential triggers reports first. The existing test was **not weakened or skipped**; reconcile the expected SQLSTATE and constraint coverage in a separately reviewed change. Because it fails, do not describe the complete native PostgreSQL suite as green.
- `npm run test:db:design`: **24/24** PGlite cases (10 original design + seven original hardening + the same seven with 005). Single-connection PGlite cannot prove concurrent security or real Supabase behavior.
- Unit **36/36**, Playwright **42/42**, Pages browser **2/2**, typecheck, production build, Pages asset verification and `git diff --check`: passed. Browser used temporary Chromium 153.0.8010.0 rather than pinned 159.0.8154.6. Frontend was not modified.
