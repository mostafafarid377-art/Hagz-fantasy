# Fantasy Friends — Phase 2A.5 final design decisions

**Scope:** Documentation-only decisions. No application code or SQL migration was changed. These decisions supplement Phase 2A.4; they do not make the SQL deployable, connect Supabase, or authorize Phase 2B by themselves.

## 1. Database target and approved baseline

**Decision: start the initial implementation on a newly provisioned, pristine Supabase project.** Do not point Phase 2B migrations at an existing/potentially populated project. There is no evidence that an existing target's match-revision history can be reconstructed reliably.

The approved design baseline is a clean schema built in dependency order from all six reviewed design scripts: `001_schema.sql` → `002_security.sql` → `003_storage.sql` → `004_integrity_workflows.sql` → `005_concurrency_hardening.sql` → `006_revision_lineage.sql`. The target must have the expected Supabase Auth and Storage schemas/roles; replay and verify the baseline first in a disposable local Supabase-compatible stack. The files remain under `supabase/design/migrations/`, not an executable Supabase migration directory. Before any actual project use, create a separately reviewed, ordered migration artifact and validate permissions, dependencies and rollback there. Do not mark individual scripts as already applied, skip 006, or apply them to a populated database.

Migration 006 aborts when *any* `match_revisions` rows already exist because migrations 001–005 did not save exact lineup-approval provenance. This is intentional fail-closed behavior, not a general populated-database migration strategy. Existing local demo data is not being imported. Any later decision to reuse a database requires a separately scoped inventory, evidence-based lineage reconstruction for every result, conflict handling and reviewed backfill/rollback plan; ambiguous rows must be quarantined, not guessed. The pristine project avoids needing that backfill for initial implementation.

## 2. Rejected correction lineup: immutable attempts, one open correction case

A correction is an immutable case rooted in the currently official result and its reason. Opening it locks the match, marks that official pointer non-current, supersedes dependent runs and marks standings stale in the same transaction. Historical result, lineup, submission and approval rows are retained. The UI must label the old result as superseded/under correction, never present it as the current official result.

Each correction-lineup attempt is a distinct immutable revision and submission. The assigned Organizer starts a *new* editable revision copied from the rejected attempt (never edits/reopens the rejected snapshot) and resubmits it under the same still-open correction case. The attempt-creation command carries a persisted request UUID and has a unique `(correction_id, attempt_no)` business key, so retries return the same attempt rather than forking history twice. The Leader independently reviews the exact new revision and records a new approval/rejection. A rejection is terminal for that attempt; the Organizer may start another numbered attempt while the same correction case remains open. Do not call `open_correction` again: there is no current official pointer to correct until the case is resolved. All attempts, reasons, actors, submissions, decisions and timestamps remain queryable.

Only the latest attempt for an open correction is eligible for approval/use. On approval, only that attempt's exact lineup revision and approval may source a result fork. A newer attempt makes any older attempt ineligible, even if its contents happen to be identical. A fresh result revision and a separate Leader result approval are still required. Publish a new current official result only after that result approval. If the result attempt itself is rejected, preserve it and its rejection; allow the Organizer to start the next numbered result attempt from the same still-current approved correction lineup, unless the lineup itself must change. A lineup change always requires a new numbered correction-lineup attempt and fresh Leader approval before another result fork.

**Approval history is not deleted or rewritten.** The original lineup/result approvals remain facts authorizing the historical result, but become ineligible as sources for the open correction. A rejected attempt's rejection remains final. Any pending submissions for a superseded attempt must be rejected as stale. If an approved correction-lineup attempt is superseded by a later attempt before result publication, its approval remains historical but no longer authorizes a result. If a later correction is opened after publication, the previously current result is marked non-current and its dependent runs are superseded; its approval remains historical. Each new correction requires a newly approved current lineup and result.

**Required implementation extension:** current 004/005 represent a correction with one immutable `match_corrections.draft_revision_id`, and 004 makes `unique(official_result_id)`; 005 requires the exact stored correction draft. They do not implement retry attempts. Phase 2B must introduce an append-only correction-attempt relation (or equivalent versioned attempt records) linking the immutable correction case, attempt number, exact lineup revision/submission/decision and prior attempt. This is a future schema/workflow change, not present in 001–006.

## 3. Result-fork idempotency

A result fork is one logical attempt sourced from one approved lineup in one workflow case. Its stable business idempotency key is `(league_id, match_id, workflow_case_id, lineup_approval_id, result_attempt_no)`, where `workflow_case_id` is the correction-case ID or a stable initial-result case ID for the non-correction flow. The persisted fork-attempt record has a unique constraint on this key and stores the one result revision it created.

The Organizer's first request allocates `result_attempt_no = 1`. Replaying that logical request returns the stored result revision, not a second draft. A genuinely new result attempt is permitted only after the preceding result submission was rejected; it gets the next attempt number and a new request idempotency UUID. Correction-lineup rejection is handled first by creating and approving a new lineup attempt, so its new approval ID scopes a distinct result-fork key. The attempt-creation request UUID is also persisted uniquely so a retried attempt-creation call cannot allocate two attempt numbers.

In one `READ COMMITTED` transaction: authenticate and authorize the assigned Organizer; lock the match and correction case; validate the case is open and the exact lineup approval is the current approved attempt; claim/lookup both the client request UUID and business key; compare stored request parameters on replay; copy the revision and children; persist the result-revision mapping and audit; commit all together. A unique-key conflict waits for the first transaction, then returns the committed mapping if the payload matches; a key reused with a different source/attempt fails with a conflict. Any error rolls back both the claim and draft. Retry the whole transaction on deadlock (`40P01`), preserving the same request UUID and business key. An explicit new attempt uses a new request UUID and next attempt number, never new keys merely because a network response was lost.

**Required implementation extension:** 006 records immutable source lineup/approval lineage but does not store this idempotency key or guarantee one fork per logical attempt. 004/006 `fork_result` is serialized by match locking but a repeated invocation can create multiple drafts. Phase 2B must persist the unique key/result mapping and exercise same-key concurrent/replay and payload-conflict cases before exposing the operation.

## 4. Organizer visibility and separation of powers

**Decision: Organizers may read only matches currently assigned to them.** Leaders retain league-wide match-review visibility. Other active league members may read approved match revisions under the existing member-visible approved-data policy. A match assignment is the exact `real_matches.organizer_id` plus active membership and matching `match_organizers` row; revoked/inactive assignments immediately lose private draft visibility after the transaction/authorization boundary.

This is a **read-only visibility decision**, never a permission to approve or mutate. Reads, writes and approval are separate checks: the assigned Organizer may submit/edit workflow drafts through future, narrow RPCs; only an active League Leader may approve/reject submissions or open a correction. Self-approval remains forbidden. RLS `SELECT` visibility alone must not grant table DML or `EXECUTE` on workflow functions. Any future mutation grant must name exact signatures and repeat authorization inside a locked trusted transaction.

Consistency review: 002 initially contains league-wide organizer read helpers, but 004 replaces match/revision read helpers with `is_match_organizer(league,match)` and narrows temporary-authorization reads; 005 and 006 preserve those helper definitions and only restore their SELECT-helper grants. Thus the final ordered 001–006 design implements assigned-match reads, not league-wide draft reads. The original 002 by itself is not the approved baseline. Actual Supabase grants and RLS composition remain unverified.

## 5. Six-migration consistency review

| Script | Consistency with these decisions | Review note |
|---|---|---|
| `001_schema.sql` | Baseline schema; no correction attempt or fork idempotency model yet. | Provides match/revision/submission/approval tables and restrictive history. 004 adds correction root; 006 adds exact source lineage. Must be applied only to pristine target under this baseline strategy. |
| `002_security.sql` | Its initial organizer reads are broader than the decision. | 004 intentionally replaces the helper/policies before the approved 001–006 baseline is complete. Never deploy/use 002 alone as final permissions. Client table privileges remain SELECT only. |
| `003_storage.sql` | No conflict with match workflow decisions. | Private referenced-image reads only; no client upload/update/delete. Requires actual Storage schema/bucket behavior verification. |
| `004_integrity_workflows.sql` | Assigned-match visibility and correction-case root align; retry and fork-idempotency do not. | Adds `is_match_organizer` and match-scoped read checks. `match_corrections` binds one draft to one old official result and is append-only; it has no attempt sequence. Its original `fork_result` has no idempotency mapping. |
| `005_concurrency_hardening.sql` | Match-bound authorization and serialization align, but idempotency/retry are absent. | Requires `READ COMMITTED`, rechecks current lineup/approval under locks and serializes forks; locking is not idempotency. Deadlocks require whole-transaction retry. |
| `006_revision_lineage.sql` | Exact lineage and fail-closed pristine baseline align. | Composite FK/check/guards bind result to exact lineup approval/revision. It replaces `fork_result` to save that lineage, but still creates a new result revision per call and has no correction-attempt or idempotency record. |

## Remaining blockers and classification

- **Before exposing match workflows in Phase 2B:** implement correction-attempt records and persisted fork idempotency. Migrations 004–006 do not yet implement the accepted design contracts; in particular 005 locking alone does not deduplicate result forks. Add replay, same-key concurrency, payload-mismatch, stale-attempt and rejection/retry tests. This is an implementation blocker, not an unresolved design choice.
- **Before any client writes or live deployment:** verify the six-script baseline in a disposable local Supabase-compatible stack, including Auth/Storage prerequisites, trusted function ownership, JWT-derived `auth.uid()`, effective grants, RLS/PostgREST composition, assigned-only organizer reads, migration replay and rollback. No live project has been accessed. Never apply 006 to populated revision data.
- **Product/operational decisions that may be completed in Phase 2B before the relevant feature:** final scoring inputs/values, event/bench/vice semantics, H2H versus fantasy-total default/ties, approved-fantasy-lineup visibility, budget scale conversion, correction UI and stale-result presentation, duplicate-person/guest eligibility proof, role delegation and leader/organizer/reviewer conflicts, schedule/time-zone and venue privacy, invitations, retention/consent and audit access, media moderation, anti-abuse/rate limits, operator recovery, lock timeout/retry and load targets, and image lifecycle. Earlier Phase 2A documents retain detailed edge cases. No unapproved scoring value or policy is implied by this report.

The retry behavior for rejected **result** attempts is decided: preserve the rejection, retry from the same still-current approved lineup using a new result-attempt number/key; if the lineup changes, require a fresh correction-lineup attempt and approval. Product may still choose rejection-reason text/UI details, not the integrity rule.
