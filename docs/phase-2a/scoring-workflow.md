# Fantasy scoring and standings design

**No scoring worker or write functions are implemented, and no official points can be created by clients.** All values except the user-specified captain multiplier and head-to-head 3/1/0 are pending product configuration. `scoring_rule_values` is deliberately empty; the tests' sample values exist only in an isolated in-memory database.

## Versioning and approvals

A leader configures a draft scoring rule set containing values by `event_type × GK/DEF/MID/FWD`, and explicit rule options for appearances/minutes, goals, assists, own goals, cards, clean sheets, result-derived wins/draws, MVP, and custom events. Before publication, validate completeness against an approved event catalog; zeros must be intentional rather than missing values. Publish immutable version N and bind each future gameweek to one published version. Reject changing a pinned version or editing published values; new policy becomes N+1, affecting only explicitly eligible future gameweeks. Product must decide whether scoring position is the fantasy position locked in lineup, actual match position, or another rule; both are captured, and this draft does not choose. The SQL columns alone do not enforce publication or immutability.

The trusted worker accepts only `official_match_results` matching a reviewed, approved result for the same revision, a previously approved lineup and the right gameweek. SQL composite FKs link official pointers to `approved/result` reviews and result submissions to an approved lineup review, but do not validate actor authorization or snapshot equality. The future transaction must validate those independently. Never use a draft, submitted, rejected, or correction-awaiting-review result. A gameweek with missing rule values, missing approved matches or disputed corrections is pending and must not be represented as finalized. When no match has been approved, there must be no positive official fantasy score fabricated from drafts; a displayed zero may only be a clearly marked pending projection, not an official result.

## Computation contract

1. Snapshot the eligible approved results, current official pointers, pinned rule version, and confirmed fantasy lineups at deadline in a single repeatable, locked snapshot. Produce a canonical input hash and unique idempotent run key. Each real player has one `match_player_performances` per approved real-match revision; duplicate event delivery must not double count, and an approved corrected revision supersedes (never adds to) the prior one.
2. Derive participation and base event points per player per real match from recorded appearances/substitutions and rules. An unparticipating player gets zero unless the pinned league-specific rules explicitly allow otherwise. Include configurable win/draw results, cards and other allowed events only once under those rules; reject ambiguous/duplicated/inconsistent events rather than guessing. Multi-match gameweeks require a confirmed aggregation and participation definition.
3. Apply the frozen fantasy lineup's bench and substitution rules (including positions and ordering) to determine eligibility for the gameweek; do not automatically include all four bench players. For each eligible owning fantasy team, independently attribute that same performance to its own lineup and preserve the scoring breakdown. Shared ownership must not multiply the real performance record.
4. Apply captain ×2 **once** per relevant eligible performance; base points × exactly one multiplier, never double multiply. If the captain did not participate, vice-captain can inherit only under the pinned league's explicit, versioned vice rules; if neither participates or neither is eligible, do not silently choose a replacement. Semantics of participation across multiple real matches, C/VC on bench and autosubs are unresolved. `fantasy_score_items` constrains ×1/×2 and arithmetic but cannot by itself ensure selection, ownership, position, event rules or only one captain; worker validation must do so.
5. Sum approved breakdowns into team/gameweek totals. For head-to-head fixtures compare the two fantasy teams' same-gameweek totals: win 3, draw 1, loss 0. Maintain separate fantasy-total and head-to-head standing projections, with fantasy points as an H2H ranking/tie criterion when the product chooses. Existing demo standings are fantasy-points-only and remain untouched. Tie rules within each mode, missing fixtures/byes, simultaneous teams, scheduling algorithm/manual oversight and the default mode require approval. No invented transfer, bonus, captain, or ranking rules.
6. Transactionally supersede a previous complete run and publish a single complete new run plus fixtures/standings only after all validations pass. Use a transactional outbox, deterministic replay and idempotent retry; compare canonical input hash and affected gameweeks. Corrections invalidate affected performance, scores, fixtures and standings as described in [match workflow](match-workflow.md); preserve old run versions for audit. Independent league policies and approved-result pointers must not leak across leagues.

## Required implementation before access

A schema relationship or FK is **not a scoring algorithm**. The draft `fantasy_scores` table cannot prove that its aggregate equals the items or came only from approved inputs, and any table owner can bypass RLS. Implement a private audited scoring worker with least privilege, a run-input relation linking every consumed official result/revision, immutable source hashes, full integrity constraints/triggers where appropriate, and controlled transactional publishing. Deny all browser writes to score tables and never expose a service-role key. Test concurrent corrections, partial failures, worker retries, stale reads, historic rule versions, multiple ownership, bench/autosub and captain/vice cases on a real local Supabase stack before release.
