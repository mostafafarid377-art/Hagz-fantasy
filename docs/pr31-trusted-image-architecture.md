# PR 31: proposed trusted image lifecycle (not implemented)

## Decision and scope

PR #31 is blocked. The existing browser → Storage → `ff_image_set` flow is not a trusted validation boundary. The server-side Sharp module is not connected to it. Neither it nor the existing reservation locks completes the requested security fix. This document specifies the smallest cohesive change that can establish the boundary; it is **not an implementation or evidence that the boundary exists**. No deployment or owner-assisted SQL is authorized by this document.

A trusted server is necessary: a static Vite app and Supabase Postgres/Storage cannot safely decode attacker-supplied image bytes merely with RLS. Reuse `server/image/validate.mjs` in a separately deployed, isolated Node service because this implementation depends on native Sharp; do not assume it runs in Supabase's Deno Edge runtime. Alternatively, replace it with an independently reviewed Edge-compatible decoder and test that exact deployed implementation. An Edge function that simply calls a publicly writable Storage bucket or trusts a client assertion is insufficient. No trusted service, protected validator attestation, or atomic final-approval replacement is implemented yet.

## Proposed enforcement chain

1. **Client → authenticated service.** The client sends bytes directly to the trusted service over HTTPS with a Supabase access token and an explicit target `(league_id, target_kind, target_id)`, expected image revision and operation ID. The service validates the token with Supabase Auth, using the returned user ID rather than any client-provided identity. Its user-scoped database request authorizes leader/player or pending-suggestion author as appropriate and creates a reservation under a row lock. A leader's approval replacement uses an approval-specific reservation tied to the exact suggestion and its expected revision; ordinary leaders cannot reserve on arbitrary managers' pending suggestions through the author-edit path. Anonymous and nonmembers are denied. Reject bad origin where relevant; CORS is not authorization. Keep credentials out of the browser and reject unsupported methods, oversized or slow requests while streaming, before buffering beyond 5 MiB.
2. **Trusted decode/re-encode.** An isolated worker with hard memory, CPU, execution-time, request and concurrency limits checks signatures and fully decodes JPEG/PNG/WebP, rejects malformed/unsupported/animated or over-dimension images, strips metadata and emits a bounded canonical PNG. Failure ends the operation without a publishable reference. Patch and pin the decoder; use adversarial input tests. Only the worker's new bytes, never input bytes or an input object key, proceed to Storage. The current primitive additionally requires isolation and request bounds; it discards appended payloads through re-encoding rather than claiming to detect all polyglots.
3. **Service → Storage.** A non-browser credential writes only the sanitized output into a private serving bucket using an unpredictable immutable server-generated key, no upsert, authoritative `image/png` metadata and appropriate safe response headers. Browsers have **no INSERT, UPDATE or DELETE** policy for this bucket; do not install the current 018 reserved INSERT/owner-read policies. The exact existing SELECT restriction must be preserved, or made strictly narrower. As PostgreSQL permissive policies combine with OR, an authorized operator must inventory *all* existing policies and grants; a restrictive new policy alone does not override a broad permissive policy. The input is never stored in this bucket, and an unbound output is not readable by any client. If quarantine storage is introduced later it must be a separate non-client-readable bucket, with separate credentials and retention.
4. **Storage → database attestation.** After successful storage of the exact output, the trusted service records a `validated` state, immutable object key, output digest/size/MIME and processing version on a reservation through a **server-only** operation. This operation must be unavailable to `anon` and `authenticated`, including through all exposed RPCs; ordinary authenticated users cannot change or create validation attestations. The server role must be narrowly scoped wherever the Supabase deployment permits; if a service-role key is the only viable way to write Storage, recognize it bypasses RLS and place it only in the isolated service with operational controls. The database cannot independently prove that service-role-written bytes are clean: the decoder, credential and service implementation are part of the trusted computing base. Reauthorize the actor and target at finalization rather than trusting an earlier reservation. Object identity must be immutable after attestation; otherwise changing bytes invalidates the guarantee. A failed attestation leaves only a non-readable orphan.
5. **Database attachment.** A single security-definer transaction locks the target and reservation in a documented consistent order, verifies exact league, target, actor, operation, current version, unexpired `validated` state and unused object; then consumes the reservation and updates image reference/version together. Database constraints/guard triggers on *all* insert/update routes, including legacy market and suggestion RPCs, must reject any non-null path without a matching validated immutable object and the precise authorized target or approval transfer. Existence in Storage, path syntax, a client MIME and reservation alone are not enough. The checks must work even if a client calls an old RPC directly, forges an object path or bypasses the UI. Revoke or safely replace legacy routes that bypass the new rules. A validated suggestion object can transfer only during approval of that exact locked suggestion and cannot be arbitrarily attached to another profile. Unreferenced outputs and staged reservations never grant client read access.
6. **Database → signed read.** Storage SELECT continues to require league membership and an actually referenced published player or permitted suggestion; the check must additionally be compatible with the validated-object invariant, not a general reservation-owner read. Only a successfully attached object receives a signed URL. The serving bucket remains private: a signed URL is a time-limited bearer capability, not public access or immediate revocation. Limit TTL, prevent sensitive URLs in logs, and verify logout/membership-change behavior. If immediate revocation is required, use an authenticated proxy rather than relying on signed URL expiry.

**Legacy external URLs:** the current UI and RPCs permit `image_url`. A universal claim that every displayed/published image is validated is impossible while arbitrary external URLs can be saved or retained. The safe default for live mode is to reject new external URLs and migrate or clear existing ones, or fetch them using a carefully isolated SSRF-resistant importer and pass the bytes through the same validator. This changes live URL functionality; preserve Demo's local images and explicitly decide legacy handling before implementing. Do not silently treat an external URL as validated. Likewise, pre-existing Storage references need an inventory and re-validation or fail-closed migration, not automatic attestation.

## Atomic lifecycle contract

Use a monotonically increasing `image_revision` for each suggestion and profile; increment on every image-path or legacy-URL change, including removal, even when the path remains NULL. All image mutations and approvals compare an explicit expected revision **after acquiring the target row lock**. A missing expected revision is not a wildcard on mutating legacy APIs. Lock ordering must be consistent across review, attach, remove, cancel, and GC to avoid deadlocks. The proposal below describes semantics, not existing behavior.

- **Begin:** under a target lock, authorize the caller and require `expected_revision`; create an operation ID tied to actor, league, target and that revision. Approval replacement is tied to the suggestion, not to a future guessed profile ID. A duplicate idempotency key with identical request returns the same operation; conflicting reuse fails.
- **Process:** validate outside the DB transaction, write sanitized immutable bytes and attest as above. This is not publication. A failed, expired or cancelled operation cannot attach.
- **Replace/remove:** under lock and after reauthorization, compare revision and require a valid bound reservation for replacement, or an explicit removal decision. Atomically set the new reference (or NULL), clear the mutually exclusive legacy URL, increment revision, consume the reservation and commit. A concurrent change makes the stale operation fail; it never restores the old image. A failed validation/storage write commits no image change.
- **Approve:** under the suggestion row lock, compare the client's selected suggestion revision and require pending status, correct league/leader and the final explicit image decision: `keep` the exact current validated suggestion image, `remove`, or `replace` with a validated approval-specific reservation for this exact suggestion and revision. Create the player and transfer the chosen reference, mark suggestion approved, consume the reservation and write the approval log **in one DB transaction**. No player record with the former image is committed for a `remove` or `replace` choice. Reject stale snapshots, changed membership, unrelated reservations and duplicate approvals. If a suggestion image edit wins first, approval's expected revision fails; if approval wins first, the edit sees a non-pending target and fails. No HTTP request, decode or Storage write occurs while holding a long-lived database lock.
- **Cancel/retry:** cancellation transitions only the caller's unused reservation to a terminal state under the same locking discipline. An in-flight worker may finish, but cannot attest or attach a cancelled/expired operation. Retrying uses an idempotency key and never automatically falls back to a prior image. If the client loses the response after commit, querying operation status reveals the committed result without repeating approval.
- **Failure and collection:** a private operator worker uses the Storage API, not direct `storage.objects` deletion. A DB transaction marks only expired/retired, globally unreferenced reservations as deleting and prevents further attach or attestation; after a grace period it deletes the immutable key, then records completion. All reference-creating paths must reject deleting state, and cleanup must be restartable and auditable. Never delete a referenced, validated-active or in-flight object; define lock order and test races. Enforce per-user/league quotas, expiration and rate limits. Do not run cleanup against hosted data without separate review.

## Required local verification before calling the blockers fixed

1. Preserve original privacy regression: unauthorized upsert and unrelated-suggestion approval cannot publish a pending image; matching approval works; cross-league, forged paths and anonymous attempts fail.
2. Exercise the actual HTTP service, real validator and database integration with an isolated Storage stand-in and real PNG/JPEG/WebP bytes. Direct client insert/update, arbitrary reserved path, fake validation flag, malicious content mislabeled as image, truncated and oversized content must not create a readable or attachable image. Verify only newly encoded bytes become referenced, never the original. Include limits, timeout, auth, reauthorization, no-service and storage/attestation failure tests.
3. Use a disposable real PostgreSQL instance with at least two independently connected sessions and explicit barriers: approval versus author attach/removal; approval versus cancellation; approval versus concurrent leader replacement; two replacements using one expected revision; retry after ambiguous response; GC versus attachment; and both commit orders. Assert the losing stale transaction fails, no old image is published on remove/replace, no duplicate player is created, and no referenced object is deleted. A single PGlite instance is **single user/connection** (`node_modules/@electric-sql/pglite/README.md`); separate sequential operations or separate in-memory databases do not establish these interleavings. The user has approved disposable local PostgreSQL and a CI PostgreSQL service. The current independent-session test suite reproduces unresolved findings; see the security review for the exact orderings and limits. The full matrix and fixed behavior remain to be implemented and verified. Never connect these tests to hosted Supabase.
4. Run all unit, typecheck, build and migration checks; retain Demo coverage and run PR CI. Local stand-ins cannot establish hosted Storage policy composition, response headers, Auth token verification, deployed worker resource limits or actual signed-URL revocation.

## Required hosted-only checks, after code and independent review

An authorized operator in an isolated non-production project must review deployment identity, all bucket policies and grants (including unexpected broad policies), storage immutability, private bucket settings, application/service credentials and function ownership; validate the deployed decoder's limits, private output, CORS, logging, error paths, signed read and bearer expiry with two accounts/two leagues. The present owner-assisted script grants client INSERT and staged SELECT and is **not** appropriate for this architecture; it must be replaced and separately reviewed, not executed as-is. No hosted SQL, storage write or deployment has been performed by this work.
