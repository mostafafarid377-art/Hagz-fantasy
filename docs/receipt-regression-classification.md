## Unhandled rejections

Four unhandled `ApiError` rejections originated at `useLive.create.test.tsx:176`, `:199` and `useLive.squad.test.tsx:76`, `:106`. The fixtures submitted before IndexedDB initialization completed and attached handlers later than the rejection. Their exact stacks and Vitest attribution appear in the baseline diagnostics. With the test storage setup and awaited asynchronous receipt handling, the full verification run completed with no unhandled errors.

## Production fixes found during investigation

- A successful receipt write passes through `verifying`; treating that as a recovery state closed the captaincy sheet and discarded selection. The squad screen now resets selection only for actual recovery phases.
- A committed squad write that completes after navigation must retain its receipt for later reconciliation without throwing into the previous screen. The provider now preserves that behavior.
- A cancelled receipt no longer returns a success to the squad UI, and a committed receipt with a failed verification read remains guarded.
- The design-026 lineup wrapper had a JSON/text fallback error (22P02); its text fallback was corrected and exercised in both database variants.
- A SQL serialization conflict from receipt execution must retain the conflict error behavior without treating a squad read as finality: the provider first serializes cancellation, then refreshes and requires review.
